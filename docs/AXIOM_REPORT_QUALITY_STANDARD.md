# Axiom Architect Report Quality Standard

## Purpose

Axiom Architect reports must feel like premium service outputs, not generic AI advice. Every report should help a client understand their workflow, make safer operating decisions, and see the next practical step.

This standard defines the required report quality model before PDF rendering, dashboard presentation, and email delivery are built.

## Benchmark

The existing Axiom Studio PDFs set the quality bar:

- A strong cover and brand system.
- A clear product overview.
- A core promise.
- Capability or deliverable tables.
- Structured sections with consistent headings.
- Practical frameworks instead of vague explanation.
- Repeatable scorecards, worksheets, tests, or action prompts.
- Calm, precise, professional language.

Axiom Architect reports should use the same level of structure, but the content must be client-specific and service-led.

## Universal Report Principles

Every report must:

1. Diagnose before recommending.
2. Separate observations, assumptions, risks, and recommendations.
3. Make missing information visible.
4. Identify where AI can support work without taking over judgement.
5. Identify where automation is appropriate, risky, premature, or unnecessary.
6. Highlight human-review triggers.
7. Give a clear next action, not only a strategic opinion.
8. Avoid unsupported claims, inflated savings promises, or vague productivity language.
9. Use Axiom Architect language: workflow architecture, operating model, review gates, automation suitability, assistant opportunity, implementation blueprint.
10. Be useful as a dashboard page first and printable/downloadable as a PDF second.

## Product-To-Report Mapping

| Product | Report type | Output promise |
| --- | --- | --- |
| Workflow Audit | Diagnostic Report | Understand one workflow, its bottlenecks, risks, and AI/automation opportunities. |
| Workflow Blueprint | Implementation Blueprint | Turn the diagnosis into a future-state workflow and 30-day implementation plan. |
| Custom Operating Pack | Operating Pack | Produce reusable protocol, assistant instructions, handoff guidance, and quality checks. |
| Workflow Stewardship | Optimisation Review | Review active workflows over time, detect drift, and recommend updates. |
| Departmental Ecosystem | Ecosystem Architecture Report | Map connected workflows, handoffs, shared data, dependencies, and implementation sequence. |
| Architect Residency | Deployment Scope Report | Define high-touch implementation needs, risks, workshops, training, and technical oversight. |

## Client-Facing Score Model

Each report should include product-relevant scores. Scores should help clients understand readiness and priority; they should not pretend to be exact science.

### Standard Score Scale

| Score | Meaning | Client interpretation |
| --- | --- | --- |
| 0-20 | Weak / undefined | The area needs clarification before reliable action. |
| 21-40 | Unstable | The workflow has material gaps or unclear operating rules. |
| 41-60 | Workable | There is enough structure to improve, but risks or friction remain. |
| 61-80 | Strong candidate | The area is suitable for structured improvement or controlled AI support. |
| 81-100 | High readiness | The area is well-defined and ready for implementation or scaling. |

### Core Client Scores

Use the relevant scores for the product. Do not force every score into every report if it does not fit the product.

| Score | What it measures | Required for |
| --- | --- | --- |
| Workflow Clarity Score | How clearly the workflow trigger, inputs, steps, owners, and outputs are defined. | All products |
| Bottleneck Severity Score | How strongly delays, duplication, rework, or unclear ownership affect the workflow. | All products |
| Automation Suitability Score | Whether parts of the workflow are stable, rule-based, and safe enough to automate. | Audit, Blueprint, Operating Pack, Ecosystem, Residency |
| AI Assistant Fit Score | Whether an assistant can support drafting, summarising, routing, checking, or preparation. | All products |
| Human Review Requirement | How much human judgement, approval, or oversight is required. | All products |
| Tool Stack Fit Score | How well current tools support the workflow. | Blueprint, Operating Pack, Stewardship, Ecosystem, Residency |
| Implementation Difficulty Score | How difficult the change is likely to be based on people, tools, data, risk, and dependencies. | Blueprint, Operating Pack, Ecosystem, Residency |
| Operating Maturity Score | How repeatable, documented, and teachable the workflow is. | Operating Pack, Stewardship, Ecosystem, Residency |
| Ecosystem Dependency Score | How strongly one workflow depends on other people, teams, systems, or data sources. | Ecosystem, Residency |
| Deployment Complexity Score | How complex the implementation is likely to be in live operations. | Residency |

### Human Review Requirement Scale

This score should be displayed as a level, not only a number.

| Level | Meaning |
| --- | --- |
| Low | The workflow can be improved with normal owner review. |
| Medium | Key outputs or decisions should be reviewed before use. |
| High | Human approval gates are required before outputs move forward. |
| Critical | The workflow may affect legal, financial, privacy, safety, hiring, customer commitments, or regulated decisions. Specialist review may be required. |

## Internal Report Quality Scorecard

Before any report is delivered, Axiom should score the report itself.

Use a 0-2 scale for each criterion:

| Criterion | Question | Score guidance |
| --- | --- | --- |
| Clarity | Can the client understand the finding quickly? | 0 weak, 1 usable, 2 strong |
| Completeness | Are the required sections present and filled? | 0 incomplete, 1 partial, 2 complete |
| Evidence | Are findings tied to intake details or clearly marked as assumptions? | 0 weak, 1 mixed, 2 strong |
| Assumptions | Are guesses, missing data, and unknowns visible? | 0 hidden, 1 partial, 2 clear |
| Risk Control | Are human-review triggers and sensitive decisions flagged? | 0 weak, 1 partial, 2 strong |
| Actionability | Does the report give practical next steps? | 0 unclear, 1 partly, 2 clear |

Readiness rule:

- 10-12: ready with normal review.
- 7-9: needs targeted fixes before delivery.
- 0-6: blocked; do not deliver until improved.

## Universal Report Sections

Every dashboard report and PDF report should follow this structure unless a product-specific format requires an extension.

1. Cover / Report Identity
   - Product name.
   - Client or business name.
   - Workflow or department name.
   - Report version.
   - Generated date.
   - Report status.

2. Executive Summary
   - What was reviewed.
   - Main finding.
   - Highest priority issue.
   - Best next action.
   - Human-review warning if relevant.

3. Intake Snapshot
   - Client context.
   - Workflow trigger.
   - Inputs.
   - Tools involved.
   - People or roles involved.
   - Desired outcome.
   - Known constraints.

4. Current-State Workflow Map
   - Trigger.
   - Inputs.
   - Steps.
   - Owners.
   - Outputs.
   - Quality checks.
   - Failure points.

5. Diagnosis
   - Friction points.
   - Bottlenecks.
   - Duplicate work.
   - Missing standards.
   - Unclear ownership.
   - Tool or data gaps.

6. Scorecard
   - Product-relevant client scores.
   - Plain-English interpretation for each score.
   - Confidence level based on intake completeness.

7. AI Assistant Opportunity Map
   - Where AI can prepare work.
   - Where AI can summarise.
   - Where AI can draft.
   - Where AI can check.
   - Where AI should not decide.

8. Automation Suitability
   - Suitable areas.
   - Unsuitable areas.
   - Areas that need standardisation first.
   - Required guardrails.

9. Risk And Review Gates
   - Human-review triggers.
   - Approval points.
   - Sensitive decisions.
   - Privacy, legal, financial, customer, safety, or staffing considerations.

10. Future-State Workflow
   - Improved workflow shape.
   - Suggested roles.
   - Suggested tool usage.
   - Assistant involvement.
   - Review gates.

11. Implementation Priorities
   - Immediate fix.
   - 7-day action plan.
   - 30-day implementation path.
   - Later improvements.

12. Upgrade Recommendation
   - Whether the client should stay with the current deliverable.
   - Whether a higher tier is genuinely useful.
   - Evidence behind the recommendation.
   - Avoid forced upsell language.

13. Assumptions And Missing Information
   - What the report assumes.
   - What was not provided.
   - What would improve confidence.

14. Delivery Notes
   - What is included.
   - What is not included.
   - Suggested client next step.

## Product-Specific Report Extensions

### Workflow Audit

Required extras:

- Diagnostic headline.
- Top 3 bottlenecks.
- Top 3 AI assistant opportunities.
- Automation suitability score.
- Risk and review notes.
- Smallest useful next step.

### Workflow Blueprint

Required extras:

- Future-state workflow diagram data.
- Recommended assistant roles.
- Review gate structure.
- Tool stack recommendations.
- 30-day implementation sequence.
- Handoff plan.

### Custom Operating Pack

Required extras:

- Operating protocol.
- Reusable instruction blocks.
- Agent or assistant role instructions.
- Implementation workbook sections.
- Quality-control checklist.
- Team handoff guide.

### Workflow Stewardship

Required extras:

- Active workflow baseline.
- Drift or error log.
- Recurring bottlenecks.
- Update recommendations.
- Tool reassessment notes.
- Next review cycle priorities.

### Departmental Ecosystem

Required extras:

- Up to five workflow maps.
- Interdependency map.
- Shared data/source-of-truth recommendations.
- Cross-team handoff logic.
- Department-level risk map.
- Quarterly implementation roadmap.

### Architect Residency

Required extras:

- Deployment scope.
- Implementation risk map.
- Workshop plan.
- Training and onboarding needs.
- Technical oversight requirements.
- Custom build or integration flags.
- Leadership decision points.

## Client-Facing Wording Rules

Use:

- "The workflow appears to..." when based on intake details.
- "Based on the information provided..." when confidence depends on client input.
- "This should be reviewed by a human before use..." for sensitive areas.
- "The strongest opportunity is..." for prioritisation.
- "Standardise this before automating it..." when the process is unstable.
- "AI can support this step by..." instead of "AI should do this."

Avoid:

- "This will save you X hours" unless supported by client-provided data.
- "Fully automate this" unless risk is low and steps are stable.
- "Guaranteed improvement."
- "AI can replace the person responsible."
- "No risk."
- Vague phrases like "streamline everything", "boost productivity", or "unlock potential" without specifics.

## Upgrade Recommendation Rules

Upgrade recommendations must be evidence-based.

### Recommend Workflow Blueprint when:

- The Audit finds a clear future-state design opportunity.
- The client needs implementation sequencing.
- There are several review gates or tool changes to plan.

### Recommend Custom Operating Pack when:

- The workflow repeats often.
- The client needs reusable instructions or team handoff material.
- Assistant instructions, checklists, or operating protocols would materially improve consistency.

### Recommend Workflow Stewardship when:

- The workflow is already active and will need ongoing updates.
- The process is likely to drift as tools, people, or workload change.
- Recurring quality review or recalibration would be useful.

### Recommend Departmental Ecosystem when:

- Multiple workflows share data, owners, tools, or handoffs.
- The problem is bigger than one process.
- Department-level sequencing is needed before implementation.

### Recommend Architect Residency when:

- Implementation is high complexity.
- There are legacy systems, integrations, workshops, technical oversight, or team training needs.
- The client needs guided deployment rather than self-directed implementation.

### Recommend no upgrade when:

- The current report fully answers the client's immediate need.
- The intake is too incomplete to justify a deeper product.
- The client needs internal clarification before buying more scope.

## Delivery Expectations

A completed Axiom Architect report should be delivered in three forms:

1. Dashboard readable page
   - Primary client experience.
   - Structured sections.
   - Easy to scan.
   - Clear status and next actions.

2. Downloadable PDF
   - Brand-quality document.
   - Uses the same report JSON.
   - Includes cover, table-style structures, report sections, scorecards, and delivery notes.
   - Versioned and stored for the client.

3. Email notification
   - Short summary only.
   - Link to dashboard report.
   - Link or prompt to download PDF.
   - Clear next step.

## Delivery Statuses

| Status | Meaning |
| --- | --- |
| draft | Report JSON created but not complete. |
| generated | AI/report engine has produced a full draft. |
| needs_review | Report requires internal/human review before delivery. |
| approved | Report passed quality checks and can be delivered. |
| delivered | Client has access through dashboard/email. |
| revision_requested | Client or reviewer requested a correction. |
| archived | Report is no longer active but remains stored. |

## Pre-Delivery Checklist

Do not deliver a report unless:

- Required product sections are present.
- Client scores include interpretations.
- Assumptions are visible.
- Risks and human-review triggers are flagged.
- Recommendations are tied to intake details.
- Upgrade recommendation is justified or set to none.
- Internal quality score is at least 10/12, or a human reviewer has approved an exception.
- Dashboard content and PDF content are derived from the same report JSON.
- Email summary does not overpromise or include sensitive details unnecessarily.

## Future PDF Production Notes

PDF rendering should be handled after the report JSON and dashboard representation are stable.

The PDF layer should not invent new report content. It should only render approved report JSON into a premium Axiom Architect document with:

- A branded cover.
- Technical grid styling.
- Product-specific title and report identity.
- Clear scorecards.
- Structured tables.
- Section dividers.
- Action plans.
- Footer/version markers.
- Download-safe layout.

Codex can be used later for the PDF rendering layer, but the content standard must remain the source of truth.
